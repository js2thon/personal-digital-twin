企业数字员工智能体平台：总体优化与实施蓝图 V1.2

> 基于 `blueprint-v1.1-implementation.md` 的升级方案。本文保留现有工程资产与已验证的安全边界，将产品目标从“个人知识数字分身”升级为“企业数字员工智能体平台”。
> 
> **核心原则：不推倒重来；先补可靠性、评估和企业级治理，再扩展岗位化能力与自动执行。**
> 
> 版本日期：2026-11-12

────────

0. 执行摘要

0.1 产品定位

建设一个支持多岗位、多角色、多组织的企业数字员工平台。平台能够从企业授权的数据源中持续学习业务知识、制度规则、岗位经验、工作流程和决策案例，为不同岗位创建具有独立认知、专业能力、沟通风格和授权边界的数字员工。

数字员工需要具备五类核心工作能力：

1. 知识理解与检索：理解企业业务语义，准确回答问题并提供证据。
2. 专业任务处理：完成岗位相关的信息整理、分析、填单、报告、工单等工作。
3. 判断与决策建议：结合事实、规则、历史案例、上下文和风险给出可解释建议。
4. 沟通与协作：通过企业 IM、邮件、OA 等渠道与员工协作，必要时发起审批或交接。
5. 受控任务执行：在明确授权、审批、额度、范围和审计条件下调用业务系统。

平台不应以“模仿某个员工的表达风格”作为唯一目标。企业数字员工首先要复现岗位职责、业务标准和组织规则；员工个人经验与风格是可选增强项，不能覆盖企业制度和岗位标准。

0.2 架构原则

• 企业知识共享，岗位认知隔离，能力组件复用，执行权限独立。
• PostgreSQL 继续作为 MVP 唯一权威事实源；不因“企业级”标签提前引入多套数据库。
• 原始证据、知识事实、企业本体、岗位认知、能力定义、决策记录、执行记录分层存储。
• 所有重要知识均可追溯到来源、证据片段、抽取版本、审核记录和有效时间。
• 先建议、后人工确认、再按动作逐项授权自动执行。
• 评估体系是 P0 基础设施，不是上线前的补充测试。
• 模型输出不是事实；模型不能自行修改权威知识、制度或授权。
• 多租户、组织隔离、数据用途和工具权限从数据模型与 API 层落实，而不是仅靠 Prompt。

0.3 对 V1.1 的总体判断

V1.1 已完成知识蒸馏、事实收口、本体版本、认知快照、问答/回复/决策三条链路、审批审计等关键闭环。当前主要问题不是缺少更多 Agent 功能，而是生产底座和质量闭环不足：

优先补齐：

1. evaluation：建立数据集、离线评估、线上反馈回流和回归门禁。
2. pgvector：启用真实向量类型、索引和完整 Embedding 生成链路。
3. worker：启用真实异步执行，API 与长任务解耦。
4. 生产部署：Docker 环境、MinIO、Redis、模型服务、备份恢复和离线运行验证。
5. 企业治理：组织/租户、岗位、数据用途、系统身份、工具授权和审计边界。
6. 岗位化建模：从单一数字分身升级为“企业知识底座 + 岗位认知配置 + 能力包 + 权限策略”。

1. 产品与领域模型

1.1 核心对象

平台建议明确以下一等领域对象：

|对象              |定义     |关键属性                |
|----------------|-------|--------------------|
|Tenant          |企业/租户边界|tenant_id、状态、数据隔离策略 |
|Organization    |企业组织单元 |部门、层级、负责人           |
|Employee        |真实员工身份 |员工编号、组织、岗位、在职状态     |
|Role            |岗位定义   |职责、输入输出、SOP、KPI、权限模板|
|DigitalEmployee |数字员工实例 |身份、岗位、认知版本、能力包、状态   |
|KnowledgeSpace  |知识空间   |企业公共、部门、项目、岗位、个人授权空间|
|Ontology        |业务语义模型 |类、关系、属性、约束、版本       |
|Skill/Capability|可复用专业能力|输入输出契约、执行步骤、工具依赖、评估集|
|Policy          |规则与权限策略|适用范围、优先级、生效时间、审批要求  |
|DecisionCase    |决策案例   |情境、证据、规则、结论、结果、复盘   |
|Workflow        |业务流程   |状态、节点、参与者、超时与补偿     |
|Tool/Connector  |外部系统连接器|身份、权限、接口契约、风险等级     |
|EvaluationSet   |评估数据集  |任务类型、标准答案、评分规则、版本   |

1.2 数字员工的组成

一个数字员工实例不应等于一个 Prompt 或一个 Agent，而应由以下配置组合：

DigitalEmployee = RoleProfile + CognitiveProfile + CapabilitySet + KnowledgeScope + PolicySet + ToolBindings + EvaluationProfile

• RoleProfile：岗位职责、工作目标、交付标准、边界和升级路径。
• CognitiveProfile：知识偏好、判断原则、沟通方式、风险倾向；必须有证据和版本。
• CapabilitySet：岗位技能与任务能力。
• KnowledgeScope：可访问的企业、部门、项目和个人知识空间。
• PolicySet：可读、可写、可执行、可外发的权限。
• ToolBindings：可调用的业务系统和 API。
• EvaluationProfile：该数字员工必须通过的岗位评估集和质量阈值。

1.3 共享与隔离原则

|层次       |共享策略                    |
|---------|------------------------|
|企业公共知识   |企业内按权限共享                |
|部门/项目知识  |按组织关系、项目成员和数据标签授权       |
|岗位知识与 SOP|同岗位可复用，发布需版本控制          |
|真实员工个人经验 |默认私有；经授权、脱敏、审核后才能沉淀为岗位经验|
|数字员工认知   |每个实例独立版本，可继承岗位模板但不能互相覆盖 |
|工具身份与执行权限|每个数字员工/任务独立授权，最小权限      |
|决策记录与执行审计|按租户、组织、任务和访问权限隔离        |

关键要求：知识共享不等于权限共享；经验可复用不等于个人数据可任意传播。

3. 企业知识、本体与认知模型

3.1 三层知识模型

不要把企业知识、岗位知识和员工个人经验混在一个“知识库”里。

A. 企业事实层

• 组织、人员、客户、供应商、产品、项目、合同、订单、资产、系统、流程等实体。
• 事实包含 subject、predicate、object/value、source、evidence、confidence、valid_time、transaction_time、status、visibility、allowed_purposes。
• 支持事实冲突、失效、取代、撤销和人工裁定。

B. 企业语义层（本体）

• 统一定义企业业务对象、关系、属性、枚举、约束和术语。
• 建议 MVP 继续采用 PostgreSQL + Pydantic/JSON Schema；将 LinkML 作为 schema-as-code 的候选，不要为了使用技术而迁移。
• 本体版本必须有变更说明、兼容性检查、审批和回滚。
• 业务部门可提交扩展提案，知识管理员审批发布。

C. 岗位经验层

• 岗位 SOP、操作规范、决策案例、常见异常、处理经验、沟通模板和质量标准。
• 经验要区分“正式制度”“岗位标准”“历史做法”“个人建议”，并标记权威等级和适用范围。
• 个人经验转为岗位经验，必须经过授权、脱敏、审核和有效性验证。

3.2 建议的企业基础本体

先建设跨行业通用骨架，再按业务域扩展，不要一开始追求大而全。

|本体域  |核心实体示例                                               |
|-----|-----------------------------------------------------|
|组织域  |Tenant、Organization、Department、Employee、Role、Position|
|业务对象域|Customer、Supplier、Product、Contract、Order、Asset       |
|项目运营域|Project、Task、Milestone、Issue、Risk、Event              |
|流程规则域|Process、Workflow、SOP、Policy、Rule、Approval            |
|知识资产域|Document、Fact、Evidence、Claim、Case、Skill              |
|系统资源域|Application、Database、API、Tool、DataAsset              |
|绩效质量域|KPI、Metric、Evaluation、Outcome、Feedback               |

实体类型和关系数量由真实业务需求驱动。MVP 可先选 15～25 个高频实体类型，优先覆盖一个试点岗位的业务闭环。

3.3 事实与证据治理

延续 V1.1 的 Claim → Evidence → Fact 设计，并补充企业级字段：

• tenant_id、knowledge_space_id
• source_id、source_version、document_id
• evidence_span、页码/段落/消息 ID
• extractor_model、prompt_version、pipeline_version
• confidence、review_status
• valid_from、valid_to、observed_at
• visibility、allowed_purposes、external_sharing
• supersedes_fact_id、conflict_group_id

必须区分：

• 业务有效时间：事实在业务世界何时成立。
• 系统记录时间：系统何时获知或写入该事实。

对制度、价格、组织架构、合同状态等易变化事实，检索时必须优先选择当前有效版本，并保留历史版本。

3.4 认知模型拆分

将当前单一 profile JSONB 逐步演进为五个逻辑子 Profile：

1. Knowledge Profile：岗位知识掌握范围、知识缺口、熟悉领域。
2. Preference Profile：处理偏好、优先级、风险容忍度及适用上下文。
3. Belief/Principle Profile：判断原则、业务假设、价值约束；必须区分事实与观点。
4. Decision Profile：决策因素、权重、阈值、例外条件和历史决策模式。
5. Communication Profile：语气、格式、沟通对象、渠道规范。

另增加 Role Profile 作为岗位标准，不与个人认知混淆。

所有 Profile 采用候选提案 → 证据聚合 → 一致性校验 → 人工确认/规则自动确认 → 新版本发布。不得通过在线强化学习直接改变生产行为。

4. 专业能力与数字员工工厂

4.1 能力（Skill/Capability）标准

每个能力必须是可测试、可复用、可授权的独立组件，至少包含：

name: invoice_review
version: 1.0.0
description: 发票审核
inputs:
  - invoice_document
  - purchase_order
  - supplier_profile
outputs:
  - review_result
  - exception_list
  - evidence_refs
preconditions:
  - user_has_access
  - required_documents_available
steps:
  - extract_invoice_fields
  - match_purchase_order
  - validate_tax_and_amount
  - detect_anomalies
  - generate_review_report
tools:
  - document_parser
  - erp_invoice_query
risk_level: medium
approval:
  required_for:
    - reject_invoice
    - submit_to_erp
evaluation_set: invoice_review_v1

能力组件应包含：

• 输入输出 Schema；
• 前置条件与后置条件；
• 标准流程与异常分支；
• 工具依赖和权限要求；
• 超时、重试、幂等和补偿策略；
• 风险等级和审批条件；
• 单元测试、评估样本和版本信息。

4.2 数字员工创建流程

1. 选择岗位模板。
2. 配置组织、职责、目标和服务对象。
3. 绑定可访问的知识空间。
4. 绑定岗位 SOP、规则和案例。
5. 选择专业能力包。
6. 配置模型、提示词和沟通规范。
7. 配置工具白名单、数据权限和审批策略。
8. 执行岗位评估与安全评估。
9. 以 Shadow Mode 观察真实任务，不产生外部副作用。
10. 通过验收后进入人工确认模式，再逐动作申请自动执行授权。

4.3 岗位模板与实例分离

岗位模板是可复用标准；数字员工实例是具体部署对象。模板升级不能直接覆盖线上实例，应生成差异、跑回归评估、审批后灰度发布。

5. Agent Runtime 与任务执行

5.1 不建议把所有任务塞进一个大 Agent

保留 V1.1 的问答、回复、决策三条图，并逐步增加任务规划和执行能力。建议按任务类型路由：

|链路           |典型任务                  |关键控制            |
|-------------|----------------------|----------------|
|QA           |查制度、查项目状态、解释业务概念      |证据充分性、引用校验      |
|Communication|回复邮件、IM、客户消息          |收件人、承诺、立场、敏感信息检查|
|Form Filling |根据多份文档填写表单            |字段级证据、置信度、冲突检测  |
|Decision     |审批建议、风险判断、方案比较        |规则校验、风险分级、审批    |
|Planning     |制定计划、拆解任务、分配资源        |目标约束、依赖关系、预算和权限 |
|Execution    |调用 ERP/CRM/OA/API 执行动作|最小权限、幂等、审批、结果核验 |
|Monitoring   |跟踪任务、异常和 SLA          |事件触发、告警、升级      |

5.2 统一任务状态机

建议任务统一采用可恢复状态机：

CREATED → CONTEXT_READY → PLANNED → WAITING_APPROVAL → RUNNING → VERIFYING → SUCCEEDED

异常状态：
NEEDS_INPUT / NEEDS_REVIEW / REJECTED / RETRY_WAIT / FAILED / CANCELLED / COMPENSATING

每个步骤记录：

• 输入摘要及引用；
• 输出结构化结果；
• 使用的模型、Prompt、能力版本；
• 工具调用参数摘要和返回摘要；
• 执行人/数字员工身份；
• 审批记录；
• 幂等键、重试次数、耗时；
• 前置与后置状态。

审批等待不得占用长期 HTTP 连接。现有 approval_tasks + HTTP approve/reject 方案可保留；后续可增加 Checkpointer 以恢复复杂推理上下文，但不是当前第一优先级。

5.3 工具执行分层

• Read：只读查询，仍需数据权限校验。
• Draft：生成草稿，不对外产生副作用。
• Write：写入业务系统，需动作授权。
• External Side Effect：发送外部消息、付款、审批通过、删除等高风险动作，默认人工审批。

所有工具经统一 Tool Gateway，不允许 Agent 直接持有数据库高权限凭据或任意访问内网地址。

6. 决策引擎与权限体系

6.1 决策模型

决策输入至少包括：

Context + Evidence + Policy + HistoricalCases + Constraints + Risk

决策输出至少包括：

• 推荐选项及备选项；
• 事实依据和规则依据；
• 关键推理因素；
• 风险与不确定性；
• 缺失信息；
• 置信度及其计算口径；
• 需要的审批人和权限；
• 可执行动作草案；
• 预期结果和回滚方案。

不要把 LLM 的自评置信度直接当作真实置信度。置信度应结合证据覆盖、来源权威性、事实冲突、模型评估表现和规则命中情况校准。

6.2 权限建议

保留现有 D0～D3 方向，但明确语义：

|级别|行为        |说明            |
|--|----------|--------------|
|D0|只读问答      |不创建外部副作用      |
|D1|生成草稿/建议   |可形成待确认内容      |
|D2|人工确认后执行   |当前默认上限        |
|D3|预授权范围内自动执行|默认关闭，逐动作、逐系统授权|

每次执行前必须同时通过：

1. 用户身份与组织关系；
2. 数字员工身份；
3. 数据可见性与用途限制；
4. 工具白名单；
5. 动作级授权；
6. 额度、频率、时间和对象范围；
7. 风险规则；
8. 审批要求；
9. 执行前状态重校验。

授权应绑定 tenant + digital_employee + tool + action + resource_scope + limit + validity_period，支持随时撤销。任何一项不满足均 fail-closed。

6.3 企业级安全补充

• Tenant 级数据隔离，数据库查询必须强制带租户上下文；可评估 PostgreSQL RLS。
• 用户、数字员工、服务账号三种主体分离。
• RBAC 管理角色，ABAC 管理数据属性与上下文策略。
• 增加 allowed_purposes、external_sharing、数据敏感级别和保留期限。
• Prompt Injection 防护：文档、邮件、网页内容一律视为不可信数据，不得作为系统指令。
• 工具调用参数校验、出站域名/IP 白名单、SSRF 防护、凭据托管与轮换。
• 敏感字段脱敏、日志最小化、密钥不入库。
• 审计日志追加写、签名校验、定期归档；HMAC 快照不能替代完整的密钥管理与防删除存储。
• 建立越权、跨租户泄露、间接提示注入和工具滥用测试集。

7. 数据接入与知识蒸馏

7.1 Connector 统一契约

建议补充通用 Connector 注册机制，而不是继续在业务代码中增加来源分支。每个 Connector 统一支持：

• validate_config
• connect
• list_changes / pull
• normalize
• get_permissions
• health_check
• checkpoint
• disconnect

每条数据至少携带：
tenant_id / source_id / source_type / source_object_id / owner / visibility / allowed_purposes / created_at / updated_at / deleted_at / sync_cursor

优先只读接入，写入业务系统必须走独立工具授权链路。

7.2 蒸馏流水线

采集 → 原始归档 → 解析 → 结构化切片 → Claim 抽取 → Evidence 定位 → 实体消歧 → 事实候选 → 本体映射 → 冲突检测 → 规则校验 → 人工审核/自动准入 → Fact 发布 → 索引更新 → 评估

自动准入条件：

• 命中已有本体；
• 来源可信且授权用途明确；
• 证据完整；
• 无未解决冲突；
• 置信度达到按字段类型校准的阈值；
• 不涉及高敏感或高影响事实。

新增本体类型、关键制度、金额、人员权限、合同状态等高风险内容，必须人工审核。

7.3 知识更新与删除

增加源数据变更、撤回、删除、权限变更的传播机制：

• 源文件更新后，定位受影响的 Claim、Evidence、Fact、Embedding 和缓存。
• 删除请求要按保留策略执行，并记录删除传播状态。
• 权限撤销必须即时影响检索和工具访问，不能只等待索引重建。
• 过期事实不物理覆盖，采用失效/取代链保留历史。
• 定期执行孤儿证据、失效向量、重复实体和权限漂移巡检。

────────

8. 检索与模型架构

8.1 混合检索

当前 pgvector 未启用是高优先级问题。建议先在 PostgreSQL 内完成：

• vector 类型；
• HNSW 或 IVFFlat 索引（按数据规模和召回测试选型）；
• 全量 Embedding 回填；
• 中文词法检索 + 向量召回 + Reranker；
• 元数据过滤前置到召回阶段；
• 证据片段级结果，而不是只返回文档级结果。

建议检索流程：

权限过滤 → Query Rewrite（可选）→ BM25/词法召回 + 向量召回 → RRF 融合 → Rerank → 时间/权威性/有效性排序 → 证据充分性判断 → 生成 → 引用验证

不要只用余弦相似度排序；企业知识检索必须考虑权威性、有效期、业务对象和权限。

8.2 模型分工

建议模型按任务分层，不追求所有任务使用最大模型：

|模型类型     |任务                    |
|---------|----------------------|
|通用推理模型   |复杂问答、决策分析、计划生成        |
|轻量模型     |分类、路由、摘要、低风险抽取        |
|Embedding|中文语义向量                |
|Reranker |检索结果精排                |
|OCR/文档模型 |PDF、扫描件、表格、版面解析       |
|规则/代码    |金额计算、字段校验、权限判断、确定性业务规则|

私有化目标应定义为数据、推理、Embedding、Reranker、日志和遥测均可在企业控制域内运行。当前 OneAPI 外部推理属于过渡状态，不能标记为完全私有化验收通过。

模型升级必须经过固定评估集回归；模型、Prompt、Embedding、Reranker 版本均应记录。

9. 评估体系：提升为 P0

这是 V1.1 当前最重要的缺口。没有评估集，不能判断数字员工是否真正学会岗位工作，也不能安全地开放自动执行。

9.1 评估分层

|评估层 |核心指标                         |
|----|-----------------------------|
|文档解析|字段/表格准确率、页码定位率、解析失败率         |
|知识蒸馏|Claim 精确率/召回率、实体消歧准确率、事实冲突识别率|
|检索  |Recall@K、MRR、NDCG、权限过滤正确率    |
|问答  |有依据回答率、事实正确率、引用准确率、拒答准确率     |
|沟通  |事实错误率、承诺违规率、语气/格式符合率         |
|表单填报|字段准确率、证据覆盖率、错误填充率、空值正确率      |
|决策  |历史案例一致性、规则符合率、风险识别率、人工采纳率    |
|执行  |工具成功率、幂等正确率、补偿成功率、越权次数       |
|安全  |跨租户泄露、越权访问、提示注入成功率、敏感信息外泄    |
|运营  |任务完成率、人工接管率、平均耗时、单位任务成本      |

9.2 基准数据集

第一阶段建议：

• QA：100～200 题；
• 岗位偏好/规范判断：50～100 题；
• 决策案例：30～50 个；
• 表单填报：按关键字段类型构建 100 份以上标注样本；
• 安全用例：覆盖越权、提示注入、跨空间访问和高风险工具调用。

数据集按岗位、业务域、难度、风险等级分层；训练/调优样本与最终测试集隔离。每个样本保留标准答案、证据、评分规则和版本。

9.3 发布门禁

任何知识抽取 Prompt、模型、检索参数、岗位 Profile、能力包或策略变更，至少执行：

1. 单元测试；
2. 离线评估集回归；
3. 安全与权限测试；
4. 关键指标对比；
5. 人工抽样验收；
6. 灰度发布和回滚准备。

D3 自动执行开放前，必须先证明评估稳定、执行可回滚、权限策略有效，并通过独立安全验收。

10.2 必须补齐的工程底座

P0：

• Alembic 数据库迁移，禁止依赖运行时散落 ALTER TABLE。
• PostgreSQL pgvector 正式启用、索引和全量向量回填。
• Redis + Celery 独立 worker，任务重试、死信、超时、幂等。
• MinIO 生产部署、生命周期、备份和恢复验证。
• Docker Compose 生产形态验证；配置、密钥和数据卷分离。
• API、Worker、模型服务健康检查和优雅关闭。
• 结构化日志、Trace ID、任务 ID、模型调用耗时和成本。
• PostgreSQL、对象存储、密钥和审计数据备份恢复演练。
• 依赖锁定、镜像扫描、SBOM、漏洞检查和制品签名。

P1：

• LangGraph Checkpointer/会话恢复；
• SSE 或 WebSocket 任务进度；
• 独立评估服务与看板；
• Connector 同步调度与增量游标；
• Outbox 事件机制，确保事实发布、索引更新和下游任务最终一致。

10.3 模块边界调整

当前 knowledge、memory、cognition 逻辑部分位于 API 层。建议逐步将业务逻辑从路由层下沉至领域服务：

• api/：协议适配、认证、参数校验。
• modules/：领域服务、用例编排和接口定义。
• repositories/：数据库读写。
• workers/：异步任务。
• connectors/：外部数据源和业务系统适配器。
• policies/：授权、风险和执行规则。
• evaluations/：数据集、评测器、报告和发布门禁。

仍保持模块化单体，不以拆微服务为目标。

11. 多租户、身份与数据权限模型

建议明确三种主体：

• Human User：真实员工/管理员/审批人。
• Digital Employee：数字员工运行身份。
• Service Identity：Connector、Worker、Tool Gateway 的服务身份。

每次请求必须同时解析：
tenant_id + user_id + organization_scope + digital_employee_id + task_id

权限判断至少包含：

• 用户是否可访问该知识；
• 数字员工是否可访问该知识；
• 当前任务是否允许使用该用途；
• 工具是否允许当前动作；
• 是否需要审批；
• 数据是否允许外发。

建议引入以下元数据：

• classification：公开、内部、机密、严格受限等；
• visibility：owner、organization、project、role、tenant 等范围；
• allowed_purposes：问答、分析、决策、训练、外发等用途；
• external_sharing：是否允许外部共享；
• retention_policy：保留期限；
• consent_ref：个人经验/个人数据授权依据。

MVP 即使只支持单企业部署，也应在表结构和服务上下文中保留 tenant 概念，避免未来重构。

12. 产品工作台

建议从当前 8 个工作区演进为：

1. 数字员工：创建、配置、启停、版本、运行状态。
2. 岗位与能力：岗位模板、SOP、技能包、能力评估。
3. 知识生产：接入、解析、蒸馏、审核、失败任务。
4. 企业知识库：事实、证据、文档、案例、规则。
5. 企业本体：实体、关系、属性、版本和扩展审批。
6. 认知管理：岗位 Profile、数字员工 Profile、认知提案。
7. 任务与决策：任务计划、决策依据、审批、执行结果。
8. 集成与工具：Connector、业务系统、MCP、工具授权。
9. 评估中心：数据集、基准测试、回归报告、质量趋势。
10. 治理与审计：组织权限、策略、审计、安全告警、成本。

首页应以“数字员工运营”作为核心，而不只是展示知识数量。建议展示：

• 各数字员工在线/运行状态；
• 今日任务量、完成率、人工接管率；
• 待审批任务和高风险任务；
• 知识新鲜度和待审核事实；
• 评估分数及版本变化；
• 工具调用异常、越权拦截和成本。

13. 实施路线图

不建议继续增加大量功能。下一阶段按“底座可靠 → 企业化建模 → 单岗位闭环 → 多岗位复制 → 受控自动化”推进。

阶段 0：V1.1 工程补强（建议 2 周）

目标：让当前系统从开发态达到可重复部署、可评估、可恢复。

交付：

• pgvector 正式启用，281 条已有切片完成向量补齐并核验。
• Evaluation 模块及第一版 QA/抽取/检索/权限基准集。
• Alembic 迁移体系。
• Redis + Celery 真 worker，关闭 eager。
• Docker Compose 端到端部署验证。
• MinIO、PostgreSQL 备份恢复演练。
• 日志、Trace、任务失败重试和告警。

验收：

• 全新环境按文档一键部署；
• API 不执行长耗时蒸馏；
• 评估集可重复运行并比较版本；
• 数据备份可恢复；
• 关键链路无未授权外部模型调用（若尚未实现本地推理，必须明确标注为过渡部署）。

阶段 1：企业领域模型与治理（建议 2～3 周）

目标：把“个人分身”升级为支持企业岗位的领域模型。

交付：

• Tenant、Organization、Employee、Role、DigitalEmployee 等核心对象。
• KnowledgeSpace 和统一权限上下文。
• 数据用途标签、外发策略和权限过滤。
• Role Profile 与 Digital Employee Profile 分离。
• 企业基础本体第一版。
• Connector 统一契约。
• 岗位模板和能力包数据结构。

验收：

• 不同组织/知识空间数据不能越权检索；
• 一个企业知识事实可被多个授权数字员工复用；
• 不同数字员工的认知、权限和运行记录互相隔离；
• 岗位模板更新不会静默覆盖已部署实例。

阶段 2：选择一个岗位做端到端 MVP（建议 3～4 周）

建议选择资料丰富、流程稳定、低风险、结果容易验证的岗位。不要同时做多个岗位。

交付：

• 一个岗位数字员工；
• 3～5 个核心能力；
• 1～2 个真实业务系统只读 Connector；
• 1 个可人工审批的写操作；
• 岗位 QA、任务、决策评估集；
• Shadow Mode 和人工确认模式；
• 任务审计与运营看板。

验收：

• 关键任务达到事先定义的准确率；
• 所有结论可追溯证据；
• 未经确认的外部副作用为 0；
• 失败任务可恢复或安全终止；
• 人工接管和反馈能进入改进队列。

阶段 3：岗位复制与能力复用（建议 4～6 周）

交付：

• 第二、第三个岗位模板；
• 能力组件复用机制；
• 岗位间协作和任务交接；
• 共享知识与隔离认知；
• 能力版本、模板版本和数字员工实例版本管理；
• 统一评估基准与岗位专项评估。

验收：

• 新岗位可通过模板和能力包配置，而非复制一套 Agent 代码；
• 共享知识更新不会破坏其他岗位的权限边界；
• 能力包变更可回归、灰度和回滚。

阶段 4：分级自动执行（持续演进）

仅对稳定、低风险、可回滚动作开放：

• 单动作授权；
• 执行额度和频率限制；
• 目标对象白名单；
• 执行前重校验；
• 失败熔断；
• 人工抽检；
• 自动撤权和回滚。

D3 不应按“数字员工整体”授权，而应按“某个数字员工在某个系统上执行某个动作、针对某类对象、在一定额度和时间范围内”授权。

14. MVP 范围建议

必须做

• 企业授权数据源接入；
• 文档/消息解析与证据级抽取；
• 企业基础本体；
• Claim/Evidence/Fact 权威知识链；
• 混合检索与引用校验；

• 数字员工实例；

• 人工审批；

暂不做

• 无法回滚的自动决策；
• 用数字员工替代真实员工的管理和责任机制。

15. 风险清单与应对

|风险           |影响        |应对                                               |
|-------------|----------|-------------------------------------------------|
|企业知识与个人经验混淆  |越权传播、错误标准化|知识空间隔离、来源标签、经验晋升审核                               |
|本体过度设计       |建设周期长、难以落地|先通用骨架 + 单岗位领域扩展                                  |
|模型幻觉         |错误回答/决策   |证据充分性、规则校验、拒答和人工复核                               |
|事实过期         |依据失效制度做判断 |双时间线、有效期、冲突和取代链                                  |
|权限仅靠 Prompt  |数据泄露和越权执行 |数据库/服务层强制授权、Tool Gateway                         |
|自动执行过早       |业务损失      |Shadow → Draft → Human Approval → Scoped Autonomy|
|评估集污染        |指标虚高      |训练/验证/测试隔离、盲测样本                                  |
|Connector 不稳定|数据不完整     |游标、幂等、重试、删除同步、健康检查                               |
|模型/Prompt 漂移 |线上质量下降    |版本锁定、回归门禁、灰度回滚                                   |
|多岗位复制靠复制代码   |维护成本快速上升  |岗位模板、能力包、统一 Runtime                              |

16. 对 V1.1 附录 B 冻结项的处理

原冻结策略整体合理，继续执行，不因产品定位升级而提前解冻。

|技术      |当前决策  |新的解冻条件                              |
|--------|------|------------------------------------|
|Neo4j   |冻结    |多跳查询、图算法或关系规模确实成为瓶颈，且 PG 方案有量化数据证明不足|
|Qdrant  |冻结    |向量规模、隔离、性能或多模态需求超过 pgvector 能力      |
|Temporal|冻结    |跨天长流程、多系统补偿和复杂调度无法由当前状态机可靠承担        |
|OPA     |冻结    |策略需要独立团队维护、跨系统统一决策或外部合规审计           |
|模型微调    |冻结    |高质量标注样本充分，基准评估证明通用模型无法达标            |
|D3      |禁止默认开放|先有稳定评估、逐动作授权、额度限制、回滚和熔断             |

新增原则：评估体系是所有复杂技术解冻和自动化授权的前置条件。

17. 需要明确的产品决策

以下事项应在进入阶段 1 前形成书面决策：

1. 首个试点企业/业务域是什么？
2. 首个数字员工对应哪个岗位，岗位职责和边界是什么？
3. 数字员工主要复现岗位标准，还是同时复现某位真实员工的个人经验？个人经验如何授权？
4. 第一批数据源有哪些，是否允许接入邮件、IM、会议和业务数据库？
5. 是否需要多租户 SaaS，还是先做单企业完全私有化部署？
6. 首个可写业务系统是什么，哪些动作允许人工审批后执行？
7. 企业制度、部门规则、岗位 SOP、个人经验冲突时，权威优先级如何定义？

在这些决策明确前，不建议先做复杂的多岗位自动协作。

18. 最终建议

V1.1 的主体代码和数据模型可以作为 V1.2 的起点。不要重写知识蒸馏、事实治理、审批审计等已经跑通的链路。

下一阶段最重要的不是再增加一个 Agent，而是完成四个转变：

1. 从个人知识库转为企业知识底座：支持组织、岗位、业务域和知识空间。
2. 从单一认知画像转为岗位认知模型：明确岗位标准、经验、判断原则和沟通规范。
3. 从 Agent 能力转为可评估的岗位能力包：每项能力有契约、权限、测试和版本。
4. 从能调用工具转为可信执行系统：所有动作可授权、可审批、可追溯、可回滚。

推荐实施顺序：

工程底座与 Evaluation → 企业领域模型与权限 → 单岗位数字员工 MVP → 多岗位模板化 → 分级自动执行

最终衡量标准不是“数字员工能不能聊天”，而是：

• 能否正确理解岗位职责；
• 能否基于企业可信知识完成任务；
• 能否复现可验证的岗位判断标准；
• 能否在权限范围内完成业务动作；
• 能否解释每个结论和动作的依据；
• 能否通过评估证明持续改进而不是持续退化。

这才是可落地、可治理、可规模化的企业数字员工平台。
